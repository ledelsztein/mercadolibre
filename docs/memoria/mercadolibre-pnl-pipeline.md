Lucas asked for a recurring P&L (Ingresos/Egresos/Resultado Bruto/Impuestos/Resultado Neto, with margen bruto and neto) covering his MercadoLibre seller account, output as both a Google Sheet and an HTML dashboard. **Major architecture change 2026-07-24**: after building out five granular `base_*` tables over several sessions ([[mercadolibre-base-ventas]], [[mercadolibre-base-envios]], [[mercadolibre-base-ads]], [[mercadolibre-base-informativa]], [[mercadolibre-base-impositiva]]), the whole P&L is now **generated from those tables**, not hand-edited. Read this file for the current pipeline; the individual `base_*` memory files have the sourcing/methodology detail for each table.

**Why this matters**: rebuilding from `base_*` caught a real bug — see "Ground-truth verification caught a real bug" below. That's the whole point of this architecture: every number in the P&L is now independently re-derivable and checkable against raw order data, not trusted blindly.

## Always verify the real system date before defining "hoy" or period cutoffs

**Recurring problem, confirmed to happen repeatedly within a single long session**: the assumed "today" drifted at least four separate times in one session (07-21→22, 22→23, 23→24, 24→27) without being noticed until Lucas pointed out a specific order/date didn't match. Each drift silently made "Hoy" and "mes parcial" stale, and caused a failed order/pack_id lookup once (searched the wrong day entirely). **Before defining or trusting any "hoy"/"parcial al X" boundary — in `build_pnl_data.py`'s `PERIODOS`, in `build_dashboard_data.py`'s, in `build_sheet.py`'s, or when answering "look up this sale" — run `date +%Y-%m-%d` (or the Python equivalent) fresh and use that, never a value carried over from earlier in the conversation.** This is exactly why `compute_base_ads.py`, `compute_base_ventas.py` etc. take explicit date arguments rather than calling `date.today()` internally — the caller (you) has to supply the real current date every time, not trust a cached belief about what day it is.

## Skills available (2026-07-27): one per table + one orchestrator that calls them as sub-skills

`.claude/skills/` has a skill for each `base_*` table (`actualizar-base-ventas`, `actualizar-base-envios`, `actualizar-base-ads`, `actualizar-base-informativa`, `actualizar-base-impositiva`) for quick single-table refreshes, plus `actualizar-tablero` which **invokes each of those five as sub-steps** (via the Skill tool, not by duplicating their instructions) and adds what they don't cover: the real-system-date check, deciding whether `base_impositiva` applies this run, regenerating `pnl_data.json`/dashboard/Sheet, and publishing. This was a deliberate refactor (2026-07-27, Lucas's request) away from an earlier version that had the same steps copy-pasted inline — single source of truth per table now lives only in that table's own skill, `actualizar-tablero` doesn't need to be kept in sync by hand when a table's methodology changes. No sale-lookup skill yet (the "explain this order" workflow, [[mercadolibre-sale-breakdown-methodology]]) — still done ad hoc each time, offered to Lucas but not yet built as of this date.

## Closed-day-only from now on — "Hoy" retired (2026-07-28)

Lucas decided to stop tracking same-day/partial-day data entirely: the tablero now only ever reports **closed days**. Concretely: `PERIODOS` in `build_pnl_data.py`/`build_dashboard_data.py`/`build_sheet.py` no longer has a `Hoy` entry — "Julio (parcial al N)" simply extends its own `fecha_hasta` up through yesterday each time the tablero runs (N moves forward by however many days passed since the last run), there's no separate same-day period anymore. Removed from the dashboard: the `Hoy` tab, its summary cards, and the whole shipping-donut panel (`SHIP_COLORS`/`renderDonut`/`renderShipping`/`shipFilterState` etc.) — donuts existed specifically for that per-day view and had no other purpose once "hoy" went away; the pivoted "Distribución de ventas por tipo de envío" table already covers shipping-type breakdown without needing "today" as a concept. When re-running `/actualizar-tablero`, the closed-day boundary is always `date_real_de_hoy - 1` — check the real system date first (see the section on that above), and don't fetch/report the current partial day at all anymore.

## Dashboard: Órdenes tab with Fecha/Order_ID filters (2026-07-28)

Added a 4th dashboard tab, `Órdenes`, so Lucas can look up a specific sale without asking in chat. `build_dashboard_data.py` now emits an `ordenes` array (every `base_ventas` record, flattened with `resultado_neto`/`margen_pct` computed the same way as the other views, `order_id`/`pack_id` as strings) — this is the full per-order detail, not aggregated. The tab has two `<input>` filters (`#filter-fecha` a date picker for exact-date match, `#filter-orderid` a text field doing substring match against both `order_id` and `pack_id` so Lucas can paste either) plus a "Limpiar filtros" button; `renderOrdenes()` re-filters and re-renders on every keystroke (`input` event), capped at `ORDENES_ROW_LIMIT = 300` rows shown at once so an unfiltered view of 400+ orders doesn't choke the table — the note above the table says how many matched and warns if the list got truncated.

**Bug found and fixed (2026-08-07)**: `renderOrdenes()` originally did `let rows = DATA.ordenes;` with no sort before filtering/slicing — the unfiltered default view showed the first 300 rows in whatever order they landed in `DATA.ordenes` (built by iterating `base_ventas.json`, a dict whose key order follows *when each order was first computed*, not sale date), not the most recent ones. With 600+ total orders and only 300 shown, Lucas's most recent day's sales could be entirely absent from the default (no-filter) view — he flagged this as "Órdenes tab isn't updated to yesterday" when the underlying `DATA.ordenes` actually did contain yesterday's rows; it was a render-order bug, not a stale-data bug. Fixed by sorting `rows` descending by `fecha` (then `order_id` as tiebreaker) before applying `ORDENES_ROW_LIMIT`, right after the filter step in `renderOrdenes()`. Lesson: **any capped/sliced list rendered from a dict-derived array needs an explicit sort** — dict insertion order is never a substitute for the sort the UI actually implies (here, "most recent first").

## `base_impositiva` had a real data-loss bug, now fixed (2026-07-28)

`compute_base_impositiva.py` used to build a fresh `registros` list from only the `period_key`s passed on the command line and overwrite `base_impositiva.json` wholesale — so running it with just a newly-closed period would silently **delete** every previously-loaded period's rows, not just leave them alone. Fixed: it now loads the existing file first, drops only the rows whose `period_key` is being recomputed in this run, and merges the fresh ones back in — same pattern as `base_ventas.json`/`base_envios.json`'s dict-keyed merge, just keyed by `period_key` instead of `order_id` since there's no natural per-row ID captured from Billing. Worth a general lesson: any script that does `json.dump(fresh_list, ...)` without first reading and merging against the existing file is a latent data-loss bug if it's ever called with a subset of what should be there — checked all the `base_*` writers for this pattern (2026-07-28) and this was the only one still doing a blind full-overwrite from a partial input.

## Current pipeline (run in this order, from `C:\Users\User\Projects\mercadolibre`)

1. **`python fetch_orders.py --status`** then agree the range with Lucas (same convention as always — report coverage, ask, never silently re-pull everything).
2. **`python fetch_orders.py <mes> <fecha_desde> <fecha_hasta>`** — merges by order id into `ordenes_<mes>.json`.
3. Update the base tables for whatever's new:
   - **`python compute_base_ventas.py <order_id_1> ... <order_id_n>`** — pass the WHOLE period's order_ids in one call (shipment proration needs siblings together). See [[mercadolibre-base-ventas]].
   - **`python compute_base_envios.py <order_id_1> ... <order_id_n>`** — same order_ids, same reasoning. See [[mercadolibre-base-envios]].
   - **`python compute_base_ads.py <fecha_desde> <fecha_hasta>`** — always rerun for the FULL mayo-hoy range, not incrementally (rewrites `base_ads.json` fully each time; cheap, no order-level API calls). See [[mercadolibre-base-ads]].
   - **`base_informativa.json`** — edit by hand when Lucas gives new invoices/gastos; ask him explicitly for anything missing, per [[mercadolibre-base-informativa]].
   - **`base_impositiva.json`** — only needs re-running (`compute_base_impositiva.py <period_key> ...`) when a NEW billing period closes; existing closed periods don't need to be redone. See [[mercadolibre-base-impositiva]].
4. **`python build_pnl_data.py`** — reads all 5 `base_*` files and regenerates `pnl_data.json` from scratch for the periods hardcoded in its `PERIODOS` dict (Mayo/Junio/Julio-parcial/Hoy with their date ranges, plus which `base_impositiva` period_key covers each — `None` if that period's billing hasn't closed yet, which makes `percepciones` stay `null`). **Edit `PERIODOS` in this script when month boundaries move** (e.g. "Julio parcial al 23" becomes "al 24" the next day) — it's the single place period definitions for the P&L totals live.
5. **`python build_dashboard_data.py`** — reads the fresh `pnl_data.json` + `base_ventas.json` + `base_envios.json` + `cat_names.json` directly (its own separate `PERIODOS` list, must stay in sync with `build_pnl_data.py`'s). Aggregates into productos/categorias/envios_tipo, writes `dashboard_data.json` and `dashboard_output.html`.
6. **`python build_sheet.py`** — same sources, updates the Sheet's `P&L`, `Rentabilidad por Producto`, `Por Categoria`, `Envios por Tipo` tabs (its own copy of `PERIODOS` too — three scripts, three copies, keep them all in sync manually since these are standalone files by design).
7. **Publish the dashboard**: copy `dashboard_output.html` to the scratchpad and call Artifact on that path (same path → same URL, https://claude.ai/code/artifact/acc4defe-62ef-46c0-8991-9ee404d96590).

## Sign conventions when reading base_ventas/base_envios into P&L math (easy to get backwards)

`base_ventas.json` records store `cargo_var_c`, `cargo_fij_c`, `costo_c`, `envio_cargo_c` as **negative** numbers (ledger-cascade display convention) but `importe_c` positive. `base_envios.json` records store `costo_c`/`ingreso_c` as **positive** magnitudes (different convention from base_ventas!). `build_pnl_data.py` negates the base_ventas fields (`cogs = -sum(costo_c)`, `cargo_venta = -sum(cargo_var_c + cargo_fij_c)`) to get the positive egreso magnitudes `pnl_data.json` expects. Get this backwards and everything looks like free money.

## Ground-truth verification caught a real bug (2026-07-24)

While rebuilding, cross-checked each period's `ventas` against the raw `sum(o['total_amount'] for o in orders if o['status']=='paid')` from `ordenes_<mes>.json` directly — completely bypassing `base_ventas` and any computed pipeline. Mayo and Julio matched exactly. **Junio did not**: the old hand-maintained `pnl_data.json` had Junio `ventas = 4,698,633.74`; the ground-truth sum was `5,685,346.83`. The ratio between them is almost exactly 1.21 — the old figure was short by nearly a full IVA factor's worth of money, for reasons not fully root-caused (not worth archaeology at this point — the point is it was *wrong*, and the new pipeline caught it because it's independently checkable against raw data, whereas the old hand-maintained number just sat there unverified). **This is the reason the base_* rebuild was worth doing** — always sanity-check a rebuilt total against a raw independent source when the numbers move by a suspicious amount (a clean ratio like 1.21, 2x, etc. is a strong signal of a real bug, not "the data changed").

## Con IVA throughout — informativo fields too

The whole P&L is on a **con IVA** basis (ventas = order `total_amount`, already con IVA; cogs = costo×1.21; cargo_venta = net commission, con IVA). For consistency, `build_pnl_data.py` pulls `importe_con_iva` (not `importe_sin_iva`) from `base_informativa` for `logistica_flex`/`otros_log`/`otros_cargos`. `autonomos`/`iibb` are tax payments with no real IVA content so con/sin IVA are equal there anyway.

## Sheet: pivoted tables instead of repeated month blocks (2026-07-24)

Lucas flagged that `Rentabilidad por Producto`, `Por Categoria`, `Envios por Tipo` repeated the same product/category/tipo names once per month (stacked blocks) — redundant. `build_sheet.py` now **pivots** all three: one row per product/categoría/tipo, with a 2-row merged header (month name spanning its metric columns, then the metric labels) and a `Total` column group at the end summing all periods. - Header merging uses `mergeCells` (`MERGE_ALL`) per month-block in row 1; `frozenRowCount` is 2 for these three tabs (vs. 1 for `P&L`), since there are two header rows now.

## stock_valorizado: daily inventory-value snapshot, not fed from orders/Facturación (2026-08-03)

Lucas asked "¿podés ver el stock valorizado de ayer?" — answer was no: the ML API only returns *current* `available_quantity`/`price` per listing, and this pipeline never stored a stock snapshot anywhere (only sales, via `base_ventas`). Offered to start snapshotting daily going forward; Lucas agreed. New table, structurally different from every other `base_*`:

- **Source**: `/users/{seller_id}/items/search` (paginated, `status=active`) + `/items?ids=...` (batch detail) — NOT Facturación, NOT orders. `compute_stock_valorizado.py` / `build_stock_valorizado_sheet.py`.
- **Excludes kits/combos**: any listing with `"bundle"` in its `tags` array is dropped. This was found and confirmed through a real back-and-forth with Lucas the same session: he flagged that composite/kit listings (e.g. "Kit Oregon Hotelero 3 Toallones + 3 Toallas + 3 Pie de Baño") shouldn't count as their own stock since they're assembled from the same individual products already counted separately — counting both would double-count inventory value. The `bundle` tag is the reliable signal (confirmed against known kit listings). **Important gotcha hit while investigating**: the first pass only checked `status=active` items and manually verified 2 already-suspected kit item_ids — missed a 3rd active kit (`MLA1763161127`, stock=7) that also had the `bundle` tag but hadn't been manually spot-checked. Second pass scanned ALL 69 items regardless of status (`items/search` with no `status` filter) and checked the `bundle` tag programmatically on every one — found 3 active kits + 8 paused/under_review ones. **Lesson: when checking "does X have property P," scan the full population programmatically — don't manually verify a couple of examples and assume that's the complete set.**
- **Only `status: active` listings count** for the actual valorized total (paused/under_review kits and non-kits alike have `available_quantity` effectively irrelevant — not currently sellable).
- **Schema**: one row per listing per day — `{fecha, item_id, sku, producto, stock, precio, importe}` where `importe = stock × precio` (list price as published, not any specific sale's actual price).
- **Merge behavior**: re-running same-day **replaces** that day's rows (upsert by `fecha`), never touches other days — this is how the historical series accumulates over time. First snapshot: 2026-08-03, 28 listings (3 kits excluded), total value $6,295,030.00.
- **Not part of the P&L** — doesn't feed `pnl_data.json`, `build_dashboard_data.py`, or `build_sheet.py`. Standalone table, own skill (`actualizar-stock-valorizado`), invoked from `actualizar-tablero` as its own step (uses TODAY's real date, not `hoy_real - 1` — this isn't sales data bound by the closed-day convention, it's "what does the catalog look like right now").
- **No backfill possible**: if Lucas asks for a date before 2026-08-03, there's no snapshot and no reliable way to reconstruct one (could estimate stock_ayer ≈ stock_hoy + ventas_de_ayer, but that assumes no restocking happened in between, which can't be verified) — say so plainly rather than guessing.

**Stray-file gotcha hit while building this (2026-08-03, worth remembering)**: an earlier one-off exploratory script (run via `Bash` with `cd` into the repo dir first) wrote its own `stock_valorizado.json` using a relative path — Python's `open()` resolves relative to the shell's cwd, not the script's own location, so it landed directly in the project directory with a different, incompatible schema (`title`/`valor` instead of `producto`/`fecha`/`importe`). The real `compute_stock_valorizado.py` crashed on `KeyError: 'fecha'` reading it. Fixed by deleting the stray file before the real script's first run. General lesson: one-off diagnostic/exploratory scripts should write their output inside the scratchpad directory explicitly (absolute path), never a bare relative filename, when they're invoked from a shell already `cd`'d into the actual project repo — a relative path silently lands in the wrong (real) location instead of erroring.

## Bug fixed: orders that go from paid → cancelled after being saved never got removed (2026-08-10)

Found during a routine `/actualizar-tablero` run: `compute_base_ventas.py` and `compute_base_envios.py` both merge new results into the existing `base_ventas.json`/`base_envios.json` (loading the file, then only ever *adding/overwriting* keys for order_ids that came back `status == 'paid'`), but neither script ever *removed* an order_id that used to be `paid` (and got saved) and later became `cancelled`/refunded. Concretely: an order was still `paid` when `compute_base_ventas.py` ran (saved normally), but had flipped to `cancelled` by the time `compute_base_envios.py` ran a few minutes later on the same order_id batch — `base_envios.json` correctly excluded it, but `base_ventas.json` kept the stale paid-era row forever, since `fetch_order_base()` returning `None` for an excluded order just means "don't touch this key," not "delete this key." This could have been silently inflating `base_ventas` with phantom cancelled orders for a while — no prior run happened to re-touch the same order_id after it flipped status, so this went undetected until now.

**Fixed in both scripts**: the `__main__` block now tracks an `excluidas` list of order_ids that came back excluded this run, and — before writing new rows — deletes each of those from the loaded `base` dict if present (`del base[str(oid)]`), with a print line so it's visible when it happens. This only self-heals for order_ids that get **re-passed** to the script in some future run (e.g. as part of the "+1 día de margen" buffer window) — it doesn't proactively re-check every historical order's current status, so a cancellation that happens well after an order's date (outside any future buffer window) could still leave a stale row undetected. If Lucas ever asks "why does this order look wrong" for something outside the recent window, re-running `compute_base_ventas.py <that order_id>` directly is the fix.

## base_full / base_adelantos: two new base_* tables for previously-uncaptured Facturación charges (2026-07-31)

Lucas noticed line items in Facturación that no `base_*` table was capturing: "Cargos de envíos Full", "Cargos por almacenamiento en Full", "Cargo por adelanto de disponibilidad de dinero en cuenta."

**First attempt was wrong and got corrected the same day using Lucas's real invoices.** Initial hypothesis (from `transaction_detail` text alone): `CFF` ("Cargo por envíos de Mercado Libre") = envío Full, `CFWA` ("Cargo por servicio de almacenamiento Full") = almacenamiento Full. This gave **~$611K for julio — wildly wrong**. Lucas caught it immediately ("es muchísimo más chico") and shared screenshots of his actual invoice's "Cargos" breakdown for two periods (julio closed + agosto in-progress). Cross-checking against those screenshots (exact-cent matches, not approximations) revealed the real mapping:

| Invoice line | Billing group | marketplace | detail_sub_type(s) | Verified against |
|---|---|---|---|---|
| "Cargos de envíos de Mercado Libre" (general, NOT Full-specific) | `ML` | `SHIPPING` | `CXD` + `CFF` | julio: `$199,719.32 + $175,818.61 = $375,537.93` = invoice net exactly. agosto: `$58,871.55 + $468,588.39 = $527,459.94` = invoice net exactly. |
| "Cargos de envíos full" (= colecta Full **+** almacenamiento Full, ML bills them as one invoice line) | `ML` | `SHIPPING` | `CFCB` ("Cargo por servicio de colecta Full" — the courier that picks up stock from the seller to bring to the warehouse) + `CFWA` ("Cargo por servicio de almacenamiento Full") | julio: `CFWA` alone = `$596.40` (CFCB had 0 entries that period — it's a newer code). agosto: `$48,587.69 CFCB + $4,113.00 CFWA = $52,700.69` = invoice exactly. |
| "Cargo por adelanto de disponibilidad de dinero en cuenta" | **`MP`** (not `ML`!) | `MP` | `CRIA` | julio: `$61,570.13`, matched invoice exactly. |

**The lesson, worth remembering for any future Facturación code investigation**: `transaction_detail` text and `detail_sub_type` naming are not reliable enough on their own to classify a charge — `CFF`'s description literally contains "Mercado Libre" generically and looked plausible as "envío Full," but it's actually the general shipping line shared with `CXD`. **Always cross-check an aggregate total against a real invoice from Lucas before trusting a code mapping** — exact-cent matches are the only real confirmation; a plausible-sounding description is not enough.

**Two new tables created**, both modeled on `compute_base_ads.py`'s architecture (day-level, Facturación-sourced, aggressive period caching — see the section below):
- **`base_full`** (`compute_base_full.py` / `build_base_full_sheet.py`): one row per day, `deposito_full_s/c` (`CFCB`+`BFCB`) + `almacenamiento_full_s/c` (`CFWA`+`BFWA`), group `ML`. **Does NOT include `CFF`/`CXD`** — those are the general shipping line, unrelated to Full.
- **`base_adelantos`** (`compute_base_adelantos.py` / `build_base_adelantos_sheet.py`): one row per day, `costo_s/c`, group **`MP`** — the one thing genuinely different from the rest of this pipeline, which otherwise only ever reads group `ML`.

**Classification, per Lucas's explicit instruction (2026-07-31)**: `cargo_colecta_full`, `cargo_almacenamiento_full`, and `adelanto` are all **Costo Variable** for the punto de equilibrio calc (see the section below on that) — added to `costos_variables` AND to `total_egresos`/`resultado_bruto` (real money that was invisible in the P&L before, not just a breakeven-only adjustment) in all three of `build_pnl_data.py`, `build_dashboard_data.py`, `build_sheet.py`. Amounts come **con IVA** from Facturación same as `base_ads` — divide by 1.21 for sin IVA, no exceptions. Lucas asked for colecta and almacenamiento to stay as **two separate P&L lines**, not combined — `dashboard_template.html`'s Egresos section has "Cargo por colecta Full" (`cargo_colecta_full`) and "Cargo por almacenamiento Full" (`cargo_almacenamiento_full`) as distinct rows, plus "Adelanto de disponibilidad de dinero" (`adelanto`).

**Real bug found and fixed while building this (2026-07-31)**: the aggressive-caching logic (see below) originally only marked a period as `periodos_cerrados` if a real invoice number (`legal_document_number`) was found in it. But a closed period can have **zero total entries** in a given billing group — confirmed for `base_adelantos`'s group `MP`, mayo/junio 2026 both returned `total: 0` for the whole group, not just zero `CRIA` entries. With the original logic, such a period would never get a discoverable factura, so `periodos_cerrados` would never be set, and the period would be re-fetched forever on every run. Fixed in all three scripts (`compute_base_ads.py`, `compute_base_full.py`, `compute_base_adelantos.py`) to cache a closed period unconditionally once it's confirmed not to be the current open one — the factura field falls back to a `'sin cargos este periodo'` placeholder string instead of blocking the cache. Group `ML` never actually hits this (always has *some* entries), so this only bit `base_adelantos` in practice, but all three were fixed for robustness.

**Confirmed real values, not a data-loss glitch**: while investigating, `base_full`'s mayo/junio periods also came back with 0 Full-related entries — verified this was genuinely $0 activity (not another rate-limit-style false empty), by cross-checking that the returned `legal_document_number` for those periods matched the already-known-good factura numbers from `base_ads`'s prior runs (`0057A00642251` for mayo, `0011A04964303` for junio) — meaning the billing fetch itself fully succeeded, it's just that Fulfillment activity genuinely started later (around July).

**Also discovered while diagnosing this**: the Billing details endpoint (`/billing/integration/periods/key/{period_key}/group/{group}/details`) enforces a real rate limit — confirmed `429 Rate limit exceeded: 5 requests per minute` during rapid back-to-back diagnostic calls. The production scripts already handle this correctly (their shared `get()` retries on 429 with a sleep), but any quick one-off diagnostic script hitting this endpoint needs the same retry-with-backoff or it'll silently look like an empty/broken response. This — plus a separate real 401 (expired `token.json` access token needing a refresh) — is the most likely explanation for the earlier same-session "0 entradas MCLICS" mystery in `base_ads` (mayo/junio briefly showed 0 instead of 30/72) that was chalked up as "transient": several back-to-back billing-heavy commands were run in a short window that day, quite plausibly tripping the same 5-req/min ceiling.

## base_ads: aggressive caching, no more full-range refetch every run (2026-07-31)

Lucas's general instruction: "en el gsheet debemos ir llamando a la info de MELI y luego guardarlo ahí, no hace falta siempre llamar a las APIs" — `base_ads` was the one table still doing a full non-incremental recompute every single run (unlike `base_ventas`/`base_envios`, which merge, and `base_impositiva`, which only fetches newly-closed periods). Rewrote `compute_base_ads.py` to cache aggressively, using a new companion file `base_ads_cache_state.json`:
- **`periodos_cerrados`** (`{period_key: factura}`): a Facturación period is fetched and permanently cached the moment it's no longer the currently-open period (i.e., the first run after it closes) — **never re-fetched again after that**, ever. The still-open period (covering "hoy") is always re-fetched, since it's still accumulating.
- **`ads_checked_hasta`**: a watermark date for the Ads API (campaign search + daily metrics) — only the date range *after* this watermark gets queried; everything up to it is trusted as already-final and skipped, even days with $0 attributed sales (so a quiet day doesn't get mistaken for "never checked").

**Known tradeoff, explicitly accepted by Lucas** (asked via AskUserQuestion, chose "cache agresivo" over "cache with revalidation" or "keep full refetch"): there's a documented case of a CLOSED Facturación period gaining $107K more when re-queried two days after closing, over a month after the period had closed. Aggressive caching means that kind of late ML-side adjustment would now be silently missed. If a cached period's numbers are ever found to be wrong, the fix is manual: delete that period's entry from `periodos_cerrados` in `base_ads_cache_state.json` to force a refetch next run — there's no automatic invalidation.

`compute_base_ads.py` is still always invoked with the full `mayo-hoy` range (per the skill) — passing the full range is cheap now, the script itself decides internally what actually needs an API call versus what's already cached. `build_base_ads_sheet.py` is unchanged (still reads `base_ads.json` fully and rewrites the tab).

**Bug also fixed in the same pass**: the Ads API (`product_ads/campaigns/search`) rejects any `date_from`/`date_to` range over 90 days (`400 invalid_request_param`) — hit this for the first time 2026-07-31 when `mayo 1 → julio 31` crossed 90 days for the first time. `compute_base_ads.py` now auto-chunks that specific API call into ≤90-day windows (`chunks_90d()`); Facturación calls are unaffected (paginated by period, no range limit). This will keep mattering as the date range grows over time even with caching, since the *watermark-forward* Ads-API sub-range itself could eventually span >90 days if the pipeline goes unrun for a long stretch.

**Transient glitch observed in the same session, unrelated to the above**: one run showed "0 entradas MCLICS" for mayo/junio (previously 30/72) — immediately re-querying Facturación directly confirmed the real data was still there (30/52+ in first page). Root cause not confirmed (likely a transient empty response treated as a valid `total=0` by `fetch_billing_once`, since 0 fetched == 0 reported doesn't trigger its inconsistency-retry logic) — a real edge case in that retry logic, but not worth hardening further given aggressive caching now makes this a one-time-per-period risk rather than a recurring one.

## Shared-shipment proration: only need ±1 day of buffer, not the whole month (2026-07-31)

`compute_base_ventas.py`/`compute_base_envios.py` used to be run with EVERY order_id in the whole month, every single refresh, because the shipment-proration logic only works correctly if all sibling orders of a shared `shipment_id` are processed together in the same invocation. That was overkill: checked empirically (2026-07-31) across all 27 shared-shipment groups found in mayo/junio/julio combined, and **zero of them span more than one calendar day** — sibling orders in the same pack are created together in a single checkout, so they always share `date_created`. Confirmed by cross-referencing `shipping.id` from the raw `ordenes_<mes>.json` records (not something stored in `base_ventas.json`/`base_envios.json` itself).

**New rule**: when refreshing, pass `compute_base_ventas.py`/`compute_base_envios.py` the order_ids for the days actually being updated **plus one calendar day of buffer before the earliest new day** — not the whole month. That's enough to guarantee every shipment-sharing group is fully covered in one call, since siblings can't span more than a single day. Updated both `actualizar-base-ventas`/`actualizar-base-envios` skills and `actualizar-tablero`'s Paso 1 to reflect this (2026-07-31) — they used to say "pasar TODAS las órdenes del período/mes en una sola llamada," now say "los días a actualizar + 1 día de margen." If this empirical finding is ever contradicted (a shared shipment IS found spanning two days), revert to whole-month reprocessing and flag it — the 1-day buffer assumption would be broken.

## Punto de equilibrio: fijo/variable classification, computed post-Resultado-Bruto, pre-impuestos (2026-07-30)

Lucas asked to split egresos into fijo/variable to get a break-even point. He gave the classification directly (not derived — don't re-classify on your own if a new cost category shows up, ask him):
- **Variable** (scales with sales): CMV (`cogs`), Cargos por ventas (`cargo_venta`), Egresos por envíos (`egreso_envio`), Logística Flex (`logistica_flex`), Otros cargos logísticos (`otros_log`).
- **Fijo**: Publicidad (`publicidad`), Otros cargos (`otros_cargos`), **Autónomos** (`autonomos`) — note Autónomos structurally lives in the P&L's "Impuestos" section (see `total_impuestos` in the pipeline math above), but for break-even purposes it counts as Costo Fijo, not as a tax. It's still displayed in the Impuestos section of the main P&L table — this reclassification only applies to the new Punto de Equilibrio block.
- **Excluded entirely** (not fijo, not variable): IIBB (`iibb`) and Percepciones/Retenciones (`percepciones`) — "son impuestos" per Lucas, kept out of the break-even calc the same way Resultado Bruto already excludes them.

Formula (mirrors the existing `margen_bruto = resultado_bruto / ventas` convention — denominator is always **Ventas**, never Total Ingresos):
```
costos_variables = cogs + cargo_venta + egreso_envio + logistica_flex + otros_log
costos_fijos = publicidad + otros_cargos + autonomos
margen_contribucion = total_ingresos - costos_variables
margen_contribucion_pct = margen_contribucion / ventas
punto_equilibrio = costos_fijos / margen_contribucion_pct   # None if margen_contribucion_pct <= 0
pct_punto_equilibrio = ventas / punto_equilibrio             # how close/over breakeven, e.g. 142% = well past it
```
`costos_variables + costos_fijos` intentionally does NOT equal `total_egresos` (autonomos isn't part of `total_egresos`, it's added in on top for this calc only) — that's expected, not a bug.

Implemented in both `build_dashboard_data.py` (per-period `m[...]` fields, feeds the dashboard) and `build_sheet.py` (own copy of the same formula, new "PUNTO DE EQUILIBRIO" block appended after "MARGEN NETO %" in the `P&L` tab rows) — same two-implementations-must-stay-in-sync pattern as `margen_bruto`/`margen_neto` elsewhere in this file. Dashboard: new "Punto de Equilibrio" section added to `PNL_ROWS` in `dashboard_template.html`, rendered by the existing generic `renderPnlTable()` (no new render function needed — reused the existing pct/result row-formatting logic). First real numbers (2026-07-30): Mayo was below breakeven (83.7% of PE), Junio and Julio were well past it (142%, 203%).

## Flex real income vs. Full/Colecta pass-through split (2026-08-18)

Lucas noticed "Ingresos por envío" in the P&L looked too high given how little he actually uses Flex, and asked which August sales were Flex. - **`compute_base_ventas.py`/`compute_base_envios.py`**: track `es_pasante` per shipment group (True exactly when the existing pass-through branch fires, i.e. `senders_cost == 0` for a Full/Colecta shipment with a real charge) and store the prorated pass-through amount as a new field per row — `envio_pasante_c`/`envio_pasante_s` in `base_ventas.json`, `pasante_c`/`pasante_s` in `base_envios.json` (note the field-name mismatch between the two files is pre-existing, not new — see the sign-convention section above).
